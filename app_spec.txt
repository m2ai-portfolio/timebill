

# TimeBill - App Specification

## Overview  
TimeBill is an automatic time‑tracking application that detects what project you're working on from terminal activity, IDE usage, and browser interaction. It runs locally on the developer’s machine, requires no internet connectivity, and stores data exclusively in a local SQLite database or in‑memory JSON structures. The tool is intended for freelancers, consultants, agencies, and contractors who bill by the hour and need an effortless way to capture billable time without manual spreadsheets or forms.

## Problem Statement  
Freelancers and consultants currently log billable hours manually using spreadsheets or forms, a process that is tedious, error‑prone, and often forgotten until invoicing time, leading to lost revenue and avoidable administrative overhead.

## Target Audience  
Freelance developers, consultants, agencies, and contractors who bill clients on an hourly basis.

## Tech Stack  
- **Language:** Python 3.11+  
- **Testing:** pytest  
- **Dependency Management:** pip (standard library only)  
- **Build Tool:** setuptools (optional)  
- **Database:** SQLite (bundled with the app) or in‑memory JSON  
- **OS:** Cross‑platform (Windows, macOS, Linux) – pure Python, no native extensions  

## Environment Setup  

### Prerequisites  
- Python 3.11 or newer installed on the host machine  
- Standard library only (no third‑party packages beyond pytest and setuptools)  

### Configuration  
| Environment Variable | Description | Default |
|----------------------|-------------|---------|
| `TIMEBILL_DB_PATH`   | Filesystem path where the SQLite database (`timebill.db`) resides | `./data/timebill.db` |
| `TIMEBILL_LOG_LEVEL` | Logging verbosity for the application (`DEBUG`, `INFO`, `WARNING`, `ERROR`) | `INFO` |
| `TIMEBILL_IDLE_SECONDS` | Number of seconds of inactivity before the agent considers the user “idle” and stops tracking | `300` (5 minutes) |
| `TIMEBILL_PROJECT_DETECTION` | Comma‑separated list of project‑identifying keywords or regex patterns used to infer the active project from window titles/process names | `""` (empty – detect by active window title only) |

## Architecture  
```
[User] <--(idle detection)--> [Agent Core] <--(local storage)--> [SQLite/JSON DB]
```
- The **Agent Core** runs in a single process, sampling OS‑level focus events, IDE plugin hooks, and browser‑tab change events every second.  
- When idle time exceeds `TIMEBILL_IDLE_SECONDS`, the agent stops accruing time for the current project.  
- All data (project mapping, accumulated seconds) is written locally to the SQLite database or held in‑memory as JSON; no external calls are made.  
- The UI is a minimal system‑tray / menu‑bar icon that opens a simple settings dialog; no web front‑end or Electron wrapper is used.

## Core Features (exactly 2–3 features, each doable in one iteration)

1. **Passive Project Detection**  
   *Description:* Infers the active project from the foreground window title, IDE status bar, or browser tab name without requiring user input.  
   *Requirements:* – Accessibility APIs for window titles (Win32/NSAccessibility, AXUIElement, etc.) – Ability to read the active process name or tab title – No UI threading; detection runs in the main thread.  

2. **Idle‑Based Time Accounting**  
   *Description:* Starts tracking when the user becomes active and stops adding time after a configurable period of inactivity.  
   *Requirements:* – Precise timestamp source (time.monotonic) – Ability to write to SQLite or in‑memory JSON storage – No floating‑point math; uses 64‑bit integer arithmetic for duration.  

3. **Local, Encrypted Storage**  
   *Description:* Persists project‑to‑seconds mappings in a SQLite database (`timebill.db`) or in‑memory JSON, encrypted with AES‑256 using a key derived from the machine‑specific UUID.  
   *Requirements:* – SQLite amalgamation or built‑in JSON support – Access to a hardware‑based RNG or OS UUID provider – No networking; all cryptographic work is performed locally with libsodium‑linked primitives.  

## Data Models  

```python
# pydantic
class Project(BaseModel):
    name: str                     # e.g. "Website Redesign"
    description: Optional[str] = None
    color: Optional[str] = None   # for UI tagging, stored as TEXT

class TimeEntry(BaseModel):
    project_name: str               # FK to Project.name
    start_ts: int                   # Unix epoch ms (UTC)
    end_ts:   Optional[int] = None
    duration_ms: int                # Computed as end_ts - start_ts
    metadata: Optional[Dict[str, str]] = None
```

## Success Criteria  
Running the following command verifies a correct implementation:  

```bash
$ python -m timebill agent
```
Expected observable outcomes (within 5 build iterations):  

1. After focusing on a‑named IDE window (e.g., `vim`), the agent begins a `TimeEntry` for project “Vim Editing”.  
2. After switching to a browser tab showing `GitHub – acme/api`, time continues to accrue for project “API Development”.  
3. After five minutes of no keyboard or mouse activity, time tracking stops and the UI tooltip displays the elapsed session time.  
4. Quitting the program exports a valid SQLite file `timebill.db` containing at least one `Project` row and zero or more `TimeEntry` rows.  
5. Restarting the agent with the same environment variables yields identical project‑name mappings and monotonic timestamps.  

## Constraints & Notes  
- **No external API calls** – all processing (focus detection, idle timing, storage, encryption) is performed locally; the tool works entirely offline.  
- **Target** – a working minimum viable product (MVP) after exactly five build iterations of the AI coding agent.  
- **Priority** – “works correctly” (the success criteria above are satisfied) over “feature complete”.  
- **Length** – total Markdown document kept between 300‑600 lines; shorter is preferred.  
- **Data** – only SQLite `.db` files **or** in‑memory JSON; no multiple storage back‑ends.  
- **Architecture** – no separate servers, workers, message queues, or micro‑services; everything runs in a single process.  
- **Features** – every feature must be specific to the *TimeBill* idea; no generic features such as “Error Handling” or “Logging”.  
- **Testing** – every test step must be a concrete CLI command with an exact, verifiable stdout; vague steps like “verify output is correct” are forbidden.  
- **If external APIs were needed** – a local alternative (mocked data, local analysis, file‑based) would be used instead.
